# MOSSY.SPACE Architecture

One-page orientation for this repo: what exists, what each piece does, how they connect, and what's live versus aspirational. Written so a new session (human or AI) can read this once and be oriented — not a changelog, not a tutorial. Verified against the code as of commit `65ea461e` (2026-08-13); re-verify anything load-bearing before relying on it if this file is old.

## What this is

MOSSY.SPACE is an Electron + React + TypeScript desktop app for Fallout 4 modding, built around an AI assistant ("Mossy") plus 23 sidebar platforms covering the full modding workflow — Creation Kit tooling, texture/asset pipelines, packaging, load-order management, and more.

## Top-level layout

| Path | What it is |
|---|---|
| `src/electron/` | Electron main process — window/app lifecycle, all IPC handlers, ESP/BGSM parsing, auto-updater, ML provider clients. Entry: `main.ts` (huge — tens of thousands of lines). |
| `src/renderer/` | The actual UI (Vite + React). By far the largest part of the app (~343 files). Entry: `index.html` → `main.tsx` → `App.tsx`. |
| `src/backend/` | Small Express server, **deployed separately to Render** (`mossy.onrender.com`). Holds the real Groq/OpenAI API keys server-side; both the Electron app and `brain-b/` call out to it for generation. Entry: `index.ts`. |
| `src/mining/` | FO4 domain-logic engines — ESP/BSA parsing, load-order optimization, conflict resolution, crash prevention, etc. Second-largest area of `src/` (83 files). No single entry point; independently-imported modules. |
| `src/shared/` | Shared types + embedded FO4 knowledge base. `types.ts` and `FO4KnowledgeBase.ts` are both very large single files. |
| `src/integrations/` | Third-party service clients: Bethel, Nexus Mods, Discord Rich Presence, Nemotron. |
| `brain-b/` | Python/Flask local AI service — retrieval + tutoring-contract router. Two variants: the developer's own GPU build (`gemma_service_enhanced.py`), and `nexus/` (CPU-only, no local model, compiled to a standalone .exe for Nexus release — see its own module docstrings for the full rationale). |
| `backend/` | **Not the same as `src/backend/`.** A separate, tiny standalone Express token server (`token-server.ts`) for OpenAI Realtime WebRTC ephemeral tokens. Easy to confuse with `src/backend/` by name alone — they're unrelated services. |
| `docs/` | The small set of *current* docs — this file, `mossy-brain-spec.md` (locked behavior/consent spec for Mossy's guided-flow features), `archive/`. |
| `docs-dev/` | ~76 files of historical fix/status/report markdown from past dev iterations. Not current documentation — a dev log, not a reference. Don't treat anything in here as ground truth without checking its date/relevance first. |
| `scripts/` | Build/dev tooling invoked from `package.json` (clean, validate, release, knowledge-sync). |
| `Mossy/` | electron-builder **output** — packaged app + `app.asar` for both editions ("Mossy NVIDIA", "Mossy Universal"). Build artifact, not source; `deploy-full.cjs` patches directly into `Mossy/<Edition>/resources/app.asar`. |
| `external/` | Knowledge-data folders (`mossy-brain-data`, `mossy-knowledge`, `volttech-dist`) — not real git submodules despite the name pattern. |
| `superpowers/`, `krita-ai-diffusion/` | Vendored third-party repos sitting in the tree, not MOSSY's own code. |

**Known repo hygiene issues** (not urgent, just don't be confused by them): the repo root has ~30 committed zero-byte junk files (single English words like `a`, `and`, `the` — almost certainly an old shell mishap that expanded a sentence into file-creation args, never cleaned up); `deploy-full.cjs` and `deploy-full.mjs` both exist but only the `.cjs` is wired into `npm run deploy`; `CHANGELOG.md` and `CHANGES.md` both exist at root; `src/components/` and `src/renderer/src/components/` are two different, confusingly-named directories (the root one only has a `guides/` subfolder — looks like an abandoned reorg).

## Build & deploy pipeline

- **`npm run build`**: validates version → Vite-compiles `src/renderer/` → `tsc`-compiles `src/electron/`+`src/main/`+`src/shared/` → runs a platform audit.
- **`npm run deploy`** = build, then `deploy-full.cjs` — a fast slim-pack deployer. It does *not* run electron-builder; it extracts the already-packaged `app.asar`, overlays fresh `dist/`+`dist-electron/` output (plus refreshed `.env.encrypted`/`CHANGELOG.md`/`package.json`), re-syncs a short required-`node_modules` list, and repacks — backing up the old asar first. This is the normal dev-iteration deploy path.
- **Full packaging** (`npm run package:win:nvidia` etc.) runs electron-builder from scratch, producing what `deploy-full.cjs` later patches for fast iteration.
- **Release publishing** is separate again — `scripts/Publish-MossyRelease.ps1`.

## The AI provider chain (verified against code, not memory — this is the part most likely to go stale)

### Cloud chat path
For the main chat surface, the fallback order inside `main.ts`'s `ai-chat-groq` handler is:
1. **Inkling** (Thinking Machines Tinker API, `thinkingmachines/Inkling`) — tried first if an API key is configured. A third, distinct provider from Groq/OpenAI.
2. **Render backend proxy** (`src/backend/routes/chat.ts`, `provider: 'groq'`) — the default path when a backend URL is configured (which it is, by default: `mossy.onrender.com`). Backend's own primary/fallback models: `openai/gpt-oss-120b` → `qwen/qwen3.6-27b` on rate-limit/context-overflow.
3. **Direct Groq SDK** — last-resort, only when no backend is reachable at all. Its own primary/fallback constants in `main.ts` are reversed from the backend's (`qwen/qwen3.6-27b` primary there) — harmless since it only activates when #2 is down, but don't assume the two "primary Groq model" constants in the codebase agree with each other.

Transcription is separate: goes through the Render backend too, but via OpenAI's `whisper-1`, not Groq.

### Local chat alternatives — all live, none dead
- **Ollama** (`src/electron/ml/ollama.ts`) — full chat-completion backend, real settings UI.
- **KoboldCpp** (`KoboldSetup.tsx`) — bundled `koboldcpp.exe` + `tinyllama`, full install/lifecycle manager, lowest-priority local fallback.
- **Brain B** — see its own section below.
- **DeepSeek-V4-Flash-0731** — lives in Ollama Settings but is actually a *hosted* Ollama Cloud model (needs `ollama signin`), not on-device.

### ⚠️ Open discrepancy — code and UI text disagree, don't assume either is authoritative
`LocalAIEngine.ts`'s actual `pickAuto()` priority order is: **`cosmos > brainb > ollama > openai_compat > koboldcpp > fo4bridge`**, with cloud only reached if no local provider is running. `localProviderPrimaryEnabled = true` confirms this is live behavior, not a disabled flag (despite an adjacent stale comment claiming the opposite). But `AIEngineSettings.tsx` and `BrainBSettings.tsx`'s own UI copy tell the user "Auto" mode is cloud-first, falling back to local. **The code and the shipped UI text contradict each other.** Verify which is actually intended before changing either — this wasn't resolved during the audit that found it.

### Image/texture/audio AI tools
All local-ComfyUI-based tools are **not bundled** — they call the user's own separately-running ComfyUI over HTTP. Licenses are annotated in-repo per tool:
- RMBG-2.0 (CC BY-NC 4.0, gated, user accepts license themselves), ComfyUI-RMBG defaults to BEN2/InSPyReNet/BEN (MIT) instead
- SUPIR upscaling — custom non-commercial license, only usable because MOSSY.SPACE stays free
- UltimateSDUpscale (GPL-3.0), IC-Light (Apache-2.0), LayerStyle (MIT), Impact-Pack (GPL-3.0), layerdiffuse (Apache-2.0)
- Knowledge Search's embeddings are **not an ML model at all** — local FNV-1a + TF-IDF hash-based, deliberately, not an oversight.

## Brain B (local retrieval + tutoring service)

Two variants, both documented in depth in their own module docstrings — this section is just the map:

- **Dev build** (`brain-b/gemma_service_enhanced.py`) — GPU-based, local Gemma model. Stays on the developer's own machine, never packaged for Nexus (same pattern as Creative Director's local-only status).
- **Nexus build** (`brain-b/nexus/brain_b_slim.py`) — CPU-only, no local model at all, retrieval via `fastembed`/ONNX, all generation routed through the same Render backend the rest of the app uses. Compiled to a standalone package via `build_nexus_package.py`, distributed via GitHub Releases, downloaded on-demand when a user clicks "Enable Brain B" (not bundled in the base installer).

**How the app calls into it (current, pre-refactor)**: `LocalAIEngine.ts` polls `{baseUrl}/health` and treats Brain B as one of the local providers in the Auto-mode priority chain above (2nd, right after `cosmos`) — when running, it's *preferred* over cloud, not merely a fallback. Any failure (not running, timeout, error) falls through to cloud silently. `BrainBSettings.tsx` is the settings UI; its "Auto mode prefers cloud" copy has the same discrepancy noted above.

### Target layer model — Brain B as enrichment, not a provider (design, 2026-08-15; not yet implemented as of this writing)

**Problem with the current shape:** Brain B is wired in as `provider === 'brainb'`, one branch in a mutually-exclusive switch alongside `ollama`/`koboldcpp`/`fo4bridge`/cloud. That's a category error — Brain B isn't a text-generation backend competing with those, it's retrieval + question-classification + a tutoring contract (check-question, learner signal) that should *wrap* whichever backend generates the actual words. The user-facing symptom: a provider picker (`AIEngineSettings.tsx`) that makes users choose between "get scene-aware tutoring" and "use my preferred model," when those aren't actually in tension. Goal: **one Mossy** — no provider picker, no "brain" language in the UI. If Brain B is installed and running, its enrichment applies automatically to every turn, regardless of which backend produces the final text; if it isn't, generation proceeds exactly as it does today with Brain B absent.

**The endpoint split.** Brain B's `/infer` currently does nine things in sequence: parse request → `classify_mode()` (mode + `scene_related`) → episodic memory search → retrieval + abstention-tier classification → the scene-exemption check (below) → learner-state update → `diagnose()` → **generation** → `contract_fields()` → response assembly. Everything except generation and `contract_fields()` can run before any text exists; `contract_fields()` cannot be pulled forward, because it takes the generated `answer` text as a direct input (`contract_fields(question, answer, mode, diagnosis)` — both `check_question` and `learner_signal` are prompted using `answer[:800]`). So the split is three pieces, not two:

- **`/enrich`** (new) — everything before generation: `classify_mode()`, episodic memory, retrieval + the abstention-tier/exemption decision, learner-state update, `diagnose()`. Returns `mode`, `scene_related`, `diagnosis`, `context_for_generation` (the scene JSON, only when the exemption below applies), citations, and — if the question genuinely abstains — the abstain response itself, so the caller can skip generation entirely.
- **generation** — dispatched through the *same* chain every non-Brain-B provider already used (Render backend / Groq cloud in `auto`, or the user's explicit Ollama choice — see "AI provider chain" above). Brain B's own local model (`infer_answer` / `run_langgraph_workflow` / `_simple_infer`) is no longer invoked as part of live serving once this lands; the code stays (nothing here deletes it), but it stops being a reachable path from the client. `diagnosis` and `context_for_generation` from `/enrich` get folded into the system instruction/prompt sent to whichever backend generates, the same way Brain B used to use them internally.
- **`/contract`** (new, thin) — called *after* generation completes, with `{question, answer, mode, diagnosis}`. Exposes the existing `contract_fields()` function as its own route; no new logic, just a new way to reach it. Returns `{check_question, learner_signal}`.
- **`/infer` stays exactly as it is**, unchanged, for the duration of the migration — nothing that calls it today breaks. Once `LocalAIEngine.ts` is migrated to call `/enrich` (+ generation + `/contract`) instead, `/infer` becomes unused but is left in place rather than deleted in this pass.

**The scene-exemption logic (preserve exactly, don't regress):** `scene_context_available = scene_related and blender_context is not None`. A question that would normally abstain (weak/no retrieval agreement against the doc corpus) is let through to generation when this is true — a low BM25 margin means nothing for "what's my active object right now," which isn't in any document corpus by nature. This check moves into `/enrich` unchanged; it's the reason `/enrich` needs `get_context`/`blender_context` as a request field, same as `/infer` does today.

**`classify_and_diagnose()` activation:** currently defined but dormant in both files (own docstring says so explicitly) — `/infer` calls `classify_mode()` and `diagnose()` as two separate `_generate_json` round-trips. Since `/enrich` now runs on *every* turn unconditionally (previously it only ran for users who'd explicitly picked Brain B), doubling its backend calls is a real cost, not a hypothetical one. `/enrich` should call the merged `classify_and_diagnose()` instead of the two separate calls.

**`LocalAIEngine.ts` changes:** delete the `provider === 'brainb'` branch and the `'brainb'` value from `LocalAiPreferred`/`pickAuto()`'s ranking entirely — it's no longer a generation candidate. Add an unconditional enrichment step at the top of `generateResponse()`: health-check Brain B, and if reachable, call `/enrich` before dispatching to whatever provider generates; if abstained, return that response directly without generating; otherwise fold `diagnosis`/`context_for_generation` into the prompt sent to the actual generator, and attach `mode`/citations to the response, then call `/contract` after generation completes for `check_question`/`learner_signal`. Brain B down or not installed → `/enrich` health-check fails fast → skip straight to generation, exactly as today's fallthrough behavior when Brain B isn't running.

**`fetchLiveBlenderContext()` trim (`LocalAIEngine.ts:178-220`):** the payload from `mossy_link_addon.py`'s `_build_scene_context()` is unbounded per-object — fine for a light scene, but nothing stops a heavy one from blowing the prompt budget once it's always being fetched (previously this only fired for the subset of users who'd deliberately chosen Brain B as their provider; making enrichment unconditional means every scene-related turn, from every user, on every provider, now carries this payload). Trim client-side before it's sent: keep FO4 export-validation results and top-level counts (`objectCount`, `meshCount`, `armatureCount`, etc.) in full — those are small and are the actual point of the feature — but reduce per-object mesh/material/modifier detail to just the active object and the current selection, replacing the rest with a count (`"otherObjects": 47`, not 47 objects' worth of vertex/UV/modifier data).

**Live Synapse (voice) currently doesn't reach any of this.** `VoiceChat.tsx` → `LiveContext.tsx` builds its system prompt via `MossyBrain.ts`'s `getFullSystemInstruction()`, which *describes* `get_context`/`get_capabilities` to the model as available tools — but no code anywhere in `src/renderer` or `src/backend` intercepts a tool-call response and executes it. Confirmed by exhaustive grep, not inferred: the only place `get_context` is ever actually fetched and used is `fetchLiveBlenderContext()`, called from exactly one place (the now-deleted `brainb` branch). So scene-aware voice questions have never worked — the model is told about a tool it has no way to invoke. Once enrichment is unconditional and provider-independent, the fix is straightforward: `LiveContext.tsx` calls the same enrichment step `LocalAIEngine.generateResponse()` now always calls (or `generateResponse()` already does it internally, since voice already delegates to `generateResponse()` at `LiveContext.tsx:468` — no separate tool-dispatch loop needs to be built). Citations, abstention, and scene context arrive on the voice path for free, as a consequence of enrichment living in one shared place instead of being reimplemented per-surface.

**Fork parity (`brain-b/check_parity.py`) constraints on this refactor:** `classify_mode`, `diagnose`, `classify_and_diagnose`, and `contract_fields` are all in `SHARED_FUNCTIONS` — any edit to any of them must be made byte-identical in both `brain-b/gemma_service_enhanced.py` and `brain-b/nexus/brain_b_slim.py`, or `check_parity.py` fails CI. `infer` itself is in `ALLOWED_TO_DIFFER` (the two files' generation step already differs — LangGraph vs. `infer_answer` directly — and that's fine by design). The new `/enrich` and `/contract` route handlers, if their logic is pulled into new top-level helper functions, need those new functions explicitly added to `SHARED_FUNCTIONS` (if they must match) or `ALLOWED_TO_DIFFER` (with a documented reason) — `check_parity.py`'s AST scan treats any new function name common to both files as an error until it's classified one way or the other. Run `python brain-b/check_parity.py` after every edit that touches both files.

### Names that aren't separate platforms
- **"Mossy Bridge"** = the **Desktop Bridge** (`BridgeServer.ts`) — screen capture, clipboard, hardware info, Blender add-on channel (port 9999), plus a `/execute` relay to Blender and various file/game/backup routes. Lives inside Runtime Hub (#18), not its own sidebar entry. **Security (2026-08-14):** was unauthenticated with wide-open CORS on a fixed port (21337) — any webpage open in any tab while Mossy ran could reach every endpoint, including a since-removed `type:'shell'` handler that ran arbitrary OS commands via Node's `exec()`. Fixed: every request now requires a locally-generated `X-Mossy-Token` header (timing-safe compared) — see `bridgeClient.ts`'s module comment and the GitHub Security Advisory for this repo. The port briefly moved to OS-assigned ephemeral as defense-in-depth alongside the token, then reverted back to fixed 21337 the same day: the released Blender add-on (`mossy_link.py`, `POINTYTHRUNDRA654/Blender-add-on.`) pushes context to a hardcoded `http://localhost:21337/blender_context`, and an install base can't be asked to reconfigure. The token is what actually secures the endpoint; port discoverability was worth little on its own and not worth breaking a shipped integration for. The renderer's own calls go through a shared `bridgeFetch()` client (`src/renderer/src/lib/bridgeClient.ts`) that discovers the live token via IPC (`get-bridge-connection`) rather than each of the ~30 call sites hand-rolling auth. The legacy standalone Python reimplementation (`mossy_server.py`, previously offered as a downloadable alternative launcher from the Desktop Bridge panel) was retired in the same fix — it had no authentication at all and bound to `0.0.0.0` (all network interfaces), strictly worse than the built-in bridge it duplicated. See "Bridge auth: current state and intended direction" below for what the current token design deliberately doesn't cover yet.
- **"Mossy Link"** = the downloadable Blender add-on itself (`public/mossy_link_addon.py`), the other end of that port-9999 channel. Not a platform/route — a bundled download, installed into Blender's own Add-ons preferences, surfaced from Runtime Hub. Binds to `127.0.0.1:9999` only (`MossyLinkServer.__init__`); auth is a locally-generated `secrets.token_hex(16)` (`_generate_secure_token()`), never an external API key, never leaves the machine. Once connected it gives Mossy real scene introspection (`_build_scene_context()` — object/mesh/armature stats, units, FPS, active action) and real FO4-specific export validation (`_build_fo4_warnings()` — FPS-pipeline mismatch, unit/scale mismatch, unapplied transforms, triangle-count vs. FO4's hard limit, missing UV layers, bone-count vs. recommended max, missing HKX pose markers), plus one-click automation presets (`_run_automation()` dispatch: `fo4_setup_scene`, `fo4_align`, `fo4_apply_transforms`, `fo4_clean_mesh`, `fo4_check`, `fo4_prep_rig`, `fo4_uv_check`, `fo4_generate_lightmap_uv`, `fo4_lod_setup`, `fo4_batch_export`). Two leftover ops from the Blender tutorial this was scaffolded from (`move_x`, `cursor_array`) are dead boilerplate, not real features — the code comments say so explicitly. Documented for the [5.6.0] release in `CHANGELOG.md`.
- **"Papyrus Studio"** = not a platform — a model-assignment *label* inside Settings → Ollama Settings ("which local model handles Papyrus generation"), used by the AI Mod Assistant and Mod Builder Hub.
- **"The F4AI relay"** = real, live HTTP server in `main.ts` on **port 8765** — receives NPC-dialogue requests from an external Python bridge (`Fallout-4-advanced-AI/`), calls Groq, optionally enriches with per-NPC memory files, returns the line. Status surfaced in Runtime Hub.

## Bridge auth: current state and intended direction

The token added 2026-08-14 (`bridgeAuthToken`) is a single, shared, full-access credential for exactly one client: Mossy's own renderer talking to its own main process. That's the right scope for what shipped — it closes a real drive-by-RCE hole immediately — but it is **not** the design for the case this architecture is actually headed toward: third-party local tools as legitimate clients of the Bridge.

**Why a single shared token doesn't extend to that case:** if a third-party tool needs to authenticate, either every tool gets handed the same all-access secret (at which point it isn't a secret — any tool, or anything that tool depends on, can now do everything the Bridge can do), or third-party tools stay unauthenticated (today's actual state, unchanged by this fix — nothing that worked before breaks, but nothing gets safer either). Neither is acceptable once "install a tool someone else wrote" is a real user action.

**The intended shape, not yet built:**
- **Per-client tokens.** Each tool gets its own token, issued through a pairing step: the tool requests access, Mossy shows the user what it's asking for in plain language ("NIF Converter wants to connect and use: file read in a folder you choose, Blender scene read"), the user approves, the tool receives a token scoped to only what it asked for.
- **Scopes are where the actual safety lives**, not the pairing UI. A mesh-format converter needs file access in one directory — it has no legitimate reason to touch clipboard, screen capture, or (now-removed) shell. A blanket token defeats the point; per-tool scoping is what makes "install a tool" not mean "give a stranger's code your whole machine."
- **Revocable per tool** from a settings panel — pairing is not a one-time irreversible grant.
- **This is also why killing the `shell` type outright (not just gating it) was the right call, not an overreaction:** with third-party tools as real clients, an arbitrary-OS-command endpoint means every tool a user ever installs has effectively unlimited machine access through Mossy, regardless of how careful the token/scope design around everything else is. Named, parameterized operations (see `/install_package` for the existing pattern: a specific package-name parameter, sanitized, not a raw command string) are the only model that scales to an actual extension point.

**Longer-term: this is most of the way to MCP already, on purpose or not.** `get_capabilities`/`call_tool` (the existing DeepSeek-OCR-2/TripoSG routing, see the "operations that flow through" table in the Bridge section above) is most of the Model Context Protocol's own vocabulary for capability discovery and invocation. Adopting the actual protocol instead of continuing a bespoke one means tools built for Mossy also work with Claude, Copilot, and anything else that speaks MCP, and vice versa — a meaningful multiplier for an open-source modding tool trying to grow a tool ecosystem, for not much more implementation cost than building the bespoke pairing flow above from scratch. Not started. Noted here so the pairing/scoping work above gets designed with this in mind from the start rather than needing a rewrite once it's adopted.

**Which add-on is canonical, resolved 2026-08-15: `public/mossy_link_addon.py` is not it.** The add-on with the actual install base is [`Blender-add-on`](https://github.com/POINTYTHRUNDRA654/Blender-add-on) (module name `blender_game_tools`, renamed 2026-08-15 from `Blender-add-on.` — the trailing period cost a 404 and a wrong conclusion about ownership before that). `public/mossy_link_addon.py` is a single-file reference implementation of the fuller v6 wire protocol (`get_context`, `get_capabilities`, `run_automation`, `export_fbx`/`export_obj`, `query_mossy`, `call_tool`, `pytorch_inference`) — useful for testing what Mossy's Bridge *expects*, but not what's actually deployed. `blender_game_tools/mossy_link.py` implements a narrower, different command set (`script`, `text`, `operator`, `set_pytorch_path` — FO4 automation goes through named Blender operators via `'operator'`, not the v6 verbs above), and its own token check (`_handle_connection`, `mossy_link.py:412-413`) is already correctly fail-closed (`if not token or cmd.get("token") != token: reject`, plus auto-generates a token on first run) — verified directly in source, not carried forward from an earlier assumption. The 2026-08-14 Bridge fix is not blocked on this add-on.

**What's actually still open: the v6 surface was never ported into the canonical repo, and per-install staleness detection doesn't exist for either add-on.** Calls like `get_context` (scene awareness, mesh-referencing answers) and `get_capabilities` fail with "Unknown command type" against `blender_game_tools` today — not an auth problem, a protocol gap. Closing it means inventorying `blender_game_tools/operators.py`'s real operator ids and either adding v6-shaped handlers there or reconstructing equivalent behavior through `'operator'` calls — deferred as of this writing (2026-08-15), tracked as its own task, not a security item. Separately, whichever add-on a user has installed, Blender has no update-notification mechanism for it — someone running an old copy of either add-on has no signal it's stale. `_build_scene_context()` in `public/mossy_link_addon.py` already returns `"addonVersion": list(bl_info["version"])` on every `get_context` call, so the plumbing to detect version drift exists for that add-on if ported; `blender_game_tools` would need the equivalent. Not built; noted here for whenever the Bridge auth UI (settings panel, pairing flow) gets worked on next, since it's a natural fit for the same surface.

## Why this division of labor works (keep it)

VS Code / an in-repo coding session has ground truth about the code and no view of licensing, platform policy, product framing, or whether an argument holds together end-to-end. A fresh reasoning-only session has the opposite. The sharpest catches in this project's history — retrieval-confidence-signal design, tokenization root-causing, license-obligation analysis, deploy/working-tree gaps — came from reasoning about a description of the system, not from reading its code directly. More repo access wouldn't have produced those catches; it risks crowding out the outside view that did. This file exists to make that outside view *accurate* without requiring full repo access — paste it at the start of a session for orientation, then reason from there.
